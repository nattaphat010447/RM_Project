สไลด์ที่ 9: MB-CGCN Architecture (2 นาที)
───────────────────────────────────────────────────────────────────────────────

โมเดล MB-CGCN มีโครงสร้างแบบ Cascading ค่ะ หมายความว่าพฤติกรรมหนึ่งส่งผล
ต่อพฤติกรรมถัดไป

เริ่มจากพฤติกรรมคลิก ผ่าน GCN 1 ชั้น ได้ embedding แล้วส่งต่อผ่าน
transformation layer ไปยังพฤติกรรมใส่ตะกร้า ซึ่งผ่าน GCN อีก 1 ชั้น
จากนั้นส่งต่อไปยังพฤติกรรมเช่าที่ผ่าน GCN 2 ชั้น

สุดท้ายนำ embedding ทั้งสามมารวมกันด้วยน้ำหนักที่เรียนรู้ได้ ผ่าน softmax
normalization ค่ะ

น้ำหนักเริ่มต้นตั้งไว้ประมาณ 0.05 สำหรับคลิก 0.15 สำหรับใส่ตะกร้า และ
0.80 สำหรับเช่า เพราะเช่าเป็นสัญญาณความสนใจที่ชัดเจนที่สุด แต่ระหว่างการ
ฝึกโมเดลจะปรับน้ำหนักเองให้เหมาะสมค่ะ

★ 1. ทำไม v2 ถึงได้ Recall สูงถึง 84% ในขณะที่ BPR loss นิ่งที่ 0.693 ตลอด?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ นี่เป็นคำถามที่สำคัญมากค่ะ ความจริงแล้ว Recall 84% นั้นสูงเกินจริงเพราะ
ข้อมูลจำลองมีแค่ 100 หนังสือ ทำให้โมเดลแนะนำถูกได้ง่าย ส่วน BPR loss ที่ติด
อยู่ที่ 0.693 ซึ่งเท่ากับ ln(2) นั้นบ่งชี้ว่า positive scores กับ negative
scores เท่ากันพอดี หมายความว่าโมเดลอาจไม่ได้เรียนรู้ความแตกต่างได้ดี แต่
เนื่องจากพื้นที่ของรายการเล็ก โมเดลยังคงแนะนำได้ในระดับหนึ่ง ดิฉันคิดว่าถ้า
ใช้ข้อมูลจริงที่มีหลายพันรายการ ค่า Recall จะลดลงมาอยู่ในระดับที่สมเหตุ
สมผลมากกว่านี้ค่ะ

(อ้างอิง: train_v2.py บรรทัด 239 temperature=0.05, evaluate_model ไม่กรอง
รายการในชุดฝึก, สไลด์ 18)

★ 2. v1 กับ v2 เปรียบเทียบกันตรง ๆ ได้ไหม เพราะค่า Recall ต่างกันมาก?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
เปรียบเทียบกันตรง ๆ ไม่ได้เลยค่ะ เพราะมีความแตกต่างหลายประการ ข้อแรก v1
ใช้ข้อมูล MyAnimeList จริง 2,113 รายการ ส่วน v2 ใช้ข้อมูลจำลอง 100 รายการ
ข้อสอง v1 วัดที่ K=20 ส่วน v2 วัดที่ K=10 ข้อสาม วิธีประเมินต่างกัน v2
ไม่ได้กรองรายการในชุดฝึกออก ทำให้ Recall สูงเกินจริง และข้อสี่ v1 มีข้อมูล
sparse มาก ส่วน v2 มีข้อมูล dense กว่า ดังนั้นตัวเลขที่เห็นไม่ได้สะท้อนว่า
v2 ดีกว่า v1 จริง ๆ แต่เป็นเพียงการแสดงให้เห็นว่าโมเดล v2 ทำงานได้บนข้อมูล
จำลองค่ะ

★ 5. v1 ใช้ค่า Recall@20 ที่ 0.0799 ซึ่งเป็นค่า peak ที่ epoch 420 ไม่ใช่
epoch 600 สุดท้าย นี่เป็น data leakage ไหม?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ นี่เป็นประเด็นที่ต้องระมัดระวังจริง ๆ ค่ะ การเลือกใช้ค่า peak จาก test
set แทนที่จะใช้ค่าที่ epoch สุดท้าย อาจถือเป็น implicit tuning บน test set
ได้ เพราะดิฉันดูว่า epoch ไหนได้ค่าดีที่สุดแล้วเลือกมา ซึ่งในงานวิจัยที่เข้มงวด
จะไม่ทำแบบนี้ แต่เนื่องจากไม่มี validation set และฝึกแค่ครั้งเดียว ดิฉันจึง
รายงานค่า peak เพื่อแสดงศักยภาพสูงสุดของโมเดล ดิฉันยอมรับว่านี่เป็นข้อจำกัด
ของวิธีการประเมิน และควรมี validation set แยกต่างหากสำหรับ early stopping
ค่ะ

(อ้างอิง: สไลด์ 15 กราฟแสดง peak ที่ epoch 420, สไลด์ 16 ตาราง Recall@20 =
0.0799)

6. ทำไมถึงเลือกใช้ MB-CGCN แทนโมเดลอื่น เช่น MMOE หรือ PLE?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ดิฉันเลือก MB-CGCN เพราะโมเดลนี้ออกแบบมาเฉพาะสำหรับพฤติกรรมแบบ
Cascading ที่มีลำดับชัดเจน เช่น คลิก → ใส่ตะกร้า → เช่า ซึ่งสอดคล้องกับ
บริบทของร้านเช่าหนังสือการ์ตูน ส่วน MMOE หรือ PLE เป็นโมเดล multi-task
ทั่วไปที่ไม่ได้สมมติว่าพฤติกรรมมีลำดับ นอกจากนี้ MB-CGCN ใช้ GCN ที่สามารถ
เรียนรู้ความสัมพันธ์ระหว่างผู้ใช้กับหนังสือผ่าน graph ได้ดี และมีกลไกน้ำหนัก
ที่ปรับได้เอง ซึ่งเหมาะกับข้อมูลที่แต่ละพฤติกรรมมีปริมาณต่างกันมากค่ะ

(อ้างอิง: สไลด์ 9 MB-CGCN Architecture, mbcgcn_v2.py adaptive_weights)

จริงน้ำหนักน่าจะกลับมาใกล้ค่าเริ่มต้นมากกว่า หรืออาจต้องปรับ loss function
ให้ให้ความสำคัญกับ RENT มากขึ้นค่ะ

8. Cold-Start Problem แก้ได้แค่ไหน มีวิธีแก้สำหรับผู้ใช้ใหม่ที่ไม่มีประวัติ

profile เบื้องต้นค่ะ

(อ้างอิง: สไลด์ 3 ปัญหา Cold-Start, สไลด์ 26 ข้อจำกัดและการพัฒนา ข้อ 5

9. ระบบจะ scale ได้แค่ไหนถ้ามีผู้ใช้และหนังสือเพิ่มขึ้นเป็นหมื่นหรือแสน

10. Ablation study ทำไหม ลองเอา CLICK หรือ CART ออกแล้วดูผลไหม?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ดิฉันไม่ได้ทำ ablation study อย่างละเอียดค่ะ เพราะข้อจำกัดด้านเวลา
และทรัพยากร แต่มีการเปรียบเทียบ v1 ที่ใช้ 2 พฤติกรรม (CART + RENT) กับ v2
ที่ใช้ 3 พฤติกรรม (CLICK + CART + RENT) ซึ่งถือเป็น ablation แบบหยาบ ๆ อยู่
แล้ว แต่เนื่องจากใช้ข้อมูลคนละชุด จึงสรุปไม่ได้ชัดเจน ในอนาคตควรทำ ablation
บนข้อมูลชุดเดียวกัน โดยลอง RENT อย่างเดียว RENT+CART และ RENT+CART+CLICK
เพื่อดูว่าแต่ละพฤติกรรมมีส่วนช่วยเพิ่มประสิทธิภาพเท่าไรค่ะ

(อ้างอิง: สไลด์ 16 v1 results, สไลด์ 20 v2 results, สไลด์ 26 ข้อจำกัด)

───────────────────────────────────────────────────────────────────────────────
11. Temperature ใน BPR loss ตั้งเป็น 0.05 ทำไมถึงเลือกค่านี้?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ temperature 0.05 เป็นค่าที่ทำให้ loss ชันขึ้น หมายความว่าโมเดลต้องแยก
positive กับ negative ให้ชัดเจนมาก ถ้า temperature ใกล้ 0 gradient จะใหญ่
มาก ถ้า temperature ใหญ่ loss จะนิ่มลง ค่า 0.05 เป็นค่าที่ดิฉันอ้างอิงจาก
งานวิจัยอื่น ๆ ที่ใช้ contrastive learning แต่ดิฉันไม่ได้ tune ค่านี้เอง และ
ไม่มีการเปรียบเทียบว่าค่าอื่นจะดีกว่าหรือไม่ ซึ่งนี่เป็นอีกจุดที่ควร tune ใน
อนาคตค่ะ

(อ้างอิง: train_v2.py บรรทัด 20-34 compute_bpr_loss, บรรทัด 239
temperature=0.05)

───────────────────────────────────────────────────────────────────────────────
12. ระบบเก็บ log พฤติกรรมทั้งหมดไหม ถ้ามีการคลิกซ้ำ ๆ จะนับทุกครั้งหรือ
นับครั้งเดียว?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ระบบเก็บ log ทุกครั้งที่มีเหตุการณ์เกิดขึ้นค่ะ ถ้าผู้ใช้คลิกหนังสือเล่ม
เดียวกันหลายครั้ง ระบบจะบันทึกทุกครั้งพร้อม timestamp แต่ในการเตรียมข้อมูล
สำหรับโมเดล ดิฉันจะรวมเป็น edge เดียวในกราฟ ไม่ได้เก็บน้ำหนักหรือจำนวนครั้ง
เพราะ MB-CGCN ใช้ binary graph ไม่ใช่ weighted graph นี่เป็นอีกจุดที่อาจปรับ
ปรุงได้ คือให้น้ำหนักกับ edge ตามความถี่ของการโต้ตอบ แต่จะต้องปรับโมเดลให้
รองรับ weighted edges ด้วยค่ะ

(อ้างอิง: prepare_data_v2.py, UserBehaviorLog ใน Django, mbcgcn_v2.py
forward ใช้ binary edges)

───────────────────────────────────────────────────────────────────────────────
13. Negative sampling ใช้ popularity-biased ทำไม ไม่ random ธรรมดาไม่ได้
หรือ?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ถ้าใช้ uniform random sampling โมเดลจะเจอ negative samples ที่ง่ายเกิน
ไป เพราะหนังสือส่วนใหญ่ไม่เป็นที่นิยม แล้วโมเดลจะเรียนรู้แยกได้ง่าย ๆ โดยไม่
ได้เรียนรู้ความแตกต่างที่ละเอียด แต่ถ้าใช้ popularity-biased sampling ที่
power 0.75 เราจะได้ negative samples ที่เป็นหนังสือยอดนิยมบ้าง ทำให้โมเดล
ต้องเรียนรู้ให้ลึกขึ้นว่าทำไมผู้ใช้ถึงไม่เลือกหนังสือยอดนิยมนี้ แต่เลือกอันอื่น
วิธีนี้ช่วยให้โมเดลแม่นยำขึ้นค่ะ

(อ้างอิง: train_v2.py บรรทัด 37-71 negative_sampling, popularity_power=0.75)

───────────────────────────────────────────────────────────────────────────────
14. ระบบรองรับการ retrain แบบ real-time ไหม หรือต้องรอจนกว่าจะสั่ง
retrain?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ระบบไม่ได้ retrain แบบ real-time ค่ะ แต่พนักงานต้องกดปุ่ม retrain จาก
หน้า admin แล้วระบบจะดึงข้อมูลล่าสุดจาก database ฝึกโมเดลใหม่ และโหลดเข้า
ระบบ ซึ่งใช้เวลาประมาณ 10-15 นาที บทคัดย่อมีการกล่าวถึง real-time แต่
จริง ๆ แล้วหมายถึงการสามารถ retrain ได้เมื่อต้องการ ไม่ใช่ทุกครั้งที่มีข้อมูล
ใหม่ เพราะจะทำให้ระบบช้ามาก ในอนาคตอาจใช้ online learning หรือ incremental
update แทนค่ะ

(อ้างอิง: retrain_model_v2.py, สไลด์ 24 การ Deploy, บทคัดย่อกล่าวถึง
real-time)

───────────────────────────────────────────────────────────────────────────────
15. ทำไมถึงใช้ L2 regularization 0.02 และไม่ลอง dropout หรือ early
stopping?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ L2 regularization 0.02 เป็นค่าที่อ้างอิงจากงานวิจัยต้นฉบับของ MB-CGCN
ค่ะ และเนื่องจากดิฉันไม่มี validation set จึงไม่ได้ทำ early stopping และ
ไม่ได้ลอง dropout เพราะ GCN ส่วนใหญ่ไม่ค่อยใช้ dropout แต่จะใช้ regularization
แทน นอกจากนี้การฝึกแค่ครั้งเดียวไม่มี hyperparameter tuning ทำให้ไม่มีการ
ทดลองค่าอื่น ๆ ซึ่งนี่เป็นข้อจำกัดของโครงงาน และในอนาคตควรทำ grid search
หรือ Bayesian optimization เพื่อหาค่าที่ดีที่สุดค่ะ

(อ้างอิง: train_v2.py บรรทัด 147 l2_reg=0.02, ไม่มี dropout หรือ early
stopping ในโค้ด)

───────────────────────────────────────────────────────────────────────────────
16. ถ้ามีหนังสือใหม่เข้ามา โมเดลจะแนะนำได้ไหม หรือต้อง retrain ก่อน?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ถ้ามีหนังสือใหม่ที่ไม่มีในโมเดลเดิม โมเดลจะแนะนำไม่ได้เลยค่ะ เพราะหนังสือ
นั้นไม่มี embedding ในโมเดล ต้อง retrain ก่อนถึงจะแนะนำได้ นี่เป็นข้อจำกัด
ของโมเดล embedding-based ทั่วไป ซึ่งต่างจาก content-based ที่ใช้ฟีเจอร์จาก
เนื้อหาแนะนำได้ทันที ในอนาคตดิฉันจึงวางแผนเพิ่มส่วน content-based เช่น
แนวเรื่อง ผู้แต่ง เพื่อให้สามารถแนะนำหนังสือใหม่ได้ก่อนที่จะมีข้อมูลโต้ตอบค่ะ

(อ้างอิง: mbcgcn_v2.py item_embedding มีขนาดคงที่, สไลด์ 26 การพัฒนาใน
อนาคต ข้อ 2)

───────────────────────────────────────────────────────────────────────────────
17. การประเมิน v2 ไม่ได้กรองรายการในชุดฝึกออก มีผลอย่างไร?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ นี่เป็นปัญหาสำคัญค่ะ ในการประเมินมาตรฐาน ควรกรองรายการที่ผู้ใช้เคยโต้ตอบ
ในชุดฝึกออกก่อนคำนวณ Recall เพราะโมเดลไม่ควรได้คะแนนจากการแนะนำของที่ผู้ใช้
รู้จักอยู่แล้ว แต่ใน v2 ฟังก์ชัน evaluate_model ไม่ได้กรอง ทำให้ Recall สูง
เกินจริง เพราะโมเดลอาจแนะนำหนังสือที่ผู้ใช้เคยเช่าในชุดฝึกมา ซึ่งไม่ใช่การค้นพบ
ใหม่ ดิฉันยอมรับว่านี่เป็นข้อผิดพลาดในการประเมิน และควรแก้ไขโดยกรอง
training items ออกก่อนค่ะ

(อ้างอิง: train_v2.py บรรทัด 74-137 evaluate_model ไม่มีการกรอง training
set)

───────────────────────────────────────────────────────────────────────────────
18. ทำ A/B Testing จริงกับผู้ใช้หรือยัง ผลเป็นอย่างไร?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ยังไม่ได้ทำ A/B Testing กับผู้ใช้จริงค่ะ ระเบียบวิธีในรายงานมีการกล่าวถึง
แผนทดสอบกับนักศึกษา 20 คน เป็นเวลา 7 วัน แต่ในความเป็นจริงยังไม่ได้ดำเนินการ
เพราะไม่มีร้านเช่าจริงที่ร่วมมือ และข้อมูลที่ใช้เป็น proxy dataset จาก
MyAnimeList ดังนั้นผลที่เห็นทั้งหมดเป็นเพียง offline evaluation เท่านั้น
ยังไม่ได้ยืนยันว่าในการใช้งานจริงจะเพิ่มยอดเช่าหรือความพึงพอใจของผู้ใช้หรือ
ไม่ นี่เป็นข้อจำกัดสำคัญและเป็นสิ่งที่ควรทำในอนาคตค่ะ

(อ้างอิง: สไลด์ 26 ข้อจำกัด, ระเบียบวิธีในรายงาน บทที่ 3)

───────────────────────────────────────────────────────────────────────────────
19. ระบบใช้ CPU หรือ GPU ในการฝึก และใช้เวลานานแค่ไหน?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ระบบฝึกบน CPU ค่ะ โดยใช้เครื่องคอมพิวเตอร์ส่วนตัว ไม่ได้ใช้คลาวด์ ใช้เวลา
ประมาณ 10-15 นาทีสำหรับ v1 ที่มีข้อมูล 4,489 ผู้ใช้ และประมาณ 5 นาทีสำหรับ
v2 ที่มีข้อมูล 100 ผู้ใช้ ค่ะ ในรายงานมีการกล่าวถึง Google Colab T4 GPU ใน
บางที่ แต่การฝึกจริงทำบนเครื่องตัวเอง ซึ่งอาจมีความคลุมเครือในรายงาน ถ้ามี
ข้อมูลมากขึ้นหรือต้องฝึกบ่อย ๆ ควรใช้ GPU เพื่อเร่งความเร็วค่ะ

(อ้างอิง: retrain_model_v2.py บรรทัด 76 device='cpu', รายงานบท 3.1.3.3
กล่าวถึงเครื่องผู้วิจัย)

───────────────────────────────────────────────────────────────────────────────
20. มีแผนจะนำระบบไปใช้จริงกับร้านเช่าไหม หรือเป็นเพียง proof-of-concept?
───────────────────────────────────────────────────────────────────────────────

คำตอบ:
ค่ะ ตอนนี้โครงงานนี้เป็น proof-of-concept ค่ะ แสดงให้เห็นว่าระบบแนะนำแบบ
หลายพฤติกรรมสามารถสร้างได้จริงและทำงานได้ แต่ยังไม่มีร้านเช่าจริงที่จะนำไป
ใช้ เพราะข้อมูลที่ใช้ฝึกเป็น proxy dataset และยังมีข้อจำกัดหลายอย่างที่ต้อง
แก้ไขก่อนจะใช้งานจริง เช่น การเก็บข้อมูลจากผู้ใช้จริง การทำ A/B Testing และ
การแก้ปัญหา Cold-Start ให้สมบูรณ์ ดิฉันหวังว่าในอนาคตจะมีโอกาสพัฒนาต่อและ
หาร้านเช่าที่สนใจทดลองใช้ระบบนี้ค่ะ

(อ้างอิง: สไลด์ 5 ขอบเขต ใช้ข้อมูล MyAnimeList, สไลด์ 26 ข้อจำกัดและการ
พัฒนาในอนาคต)

ส่วนที่ 3: ข้อสังเกตที่ควรแก้ก่อนนำเสนอ
═══════════════════════════════════════════════════════════════════════════════

1. ความไม่สอดคล้องของค่า Recall v1
   สไลด์ 20/21 และตาราง 18 ใช้ค่า 0.0799 ซึ่งเป็น peak ที่ epoch 420
   แต่ตาราง 16 แสดงค่าที่ epoch 600 = 0.0708
   → ควรชี้แจงชัดเจนในสไลด์ว่าใช้ค่า peak และอธิบายเหตุผล

2. BPR loss ใน v2 นิ่งที่ 0.6931
   ค่านี้เท่ากับ ln(2) แสดงว่าโมเดลอาจไม่ได้เรียนรู้ แต่ Recall สูง
   → ควรอธิบายไว้ล่วงหน้าว่านี่เป็นผลจากข้อมูลจำลองขนาดเล็ก

3. v2 ไม่กรอง training items ในการประเมิน
   evaluate_model ใน train_v2.py ไม่ได้กรองรายการในชุดฝึกออก ทำให้ Recall
   สูงเกินจริง
   → ควรแก้โค้ดหรือระบุไว้ชัดเจนในข้อจำกัด

4. ความคลุมเครือเรื่องการใช้ GPU/CPU
   รายงานบางที่บอกว่าใช้เครื่องผู้วิจัย บางที่บอกว่าใช้ Google Colab T4
   → ควรตรวจสอบและแก้ไขให้ตรงกัน (จริงคือใช้ CPU บนเครื่องตัวเอง)

5. A/B Testing ยังไม่ได้ทำ
   ระเบียบวิธีบอกว่าจะทดลองกับนักศึกษา 20 คน 7 วัน แต่ไม่มีผลในรายงาน
   → ควรระบุชัดว่ายังไม่ได้ทำ หรือลบออกจากระเบียบวิธี

6. ขนาด embedding dimension v1
   รายงานบอกว่า 64 มิติ แต่โค้ด backend/recommender.py อาจใช้ 32
   → ควรตรวจสอบและแก้ให้ตรงกัน (จริงคือ v1 ใช้ 64, backend เก่าอาจใช้ 32)

7. ไม่มี validation set และ statistical test
   ควรเน้นย้ำในข้อจำกัดว่านี่เป็นสาเหตุที่ผลอาจไม่ robust และต้องระวัง
   การ overgeneralize

8. คำว่า "real-time" ในบทคัดย่อ
   อาจทำให้เข้าใจผิดว่าระบบ retrain แบบ automatic แต่จริง ๆ ต้องกดปุ่มเอง
   → ควรใช้คำว่า "on-demand retraining" แทน
